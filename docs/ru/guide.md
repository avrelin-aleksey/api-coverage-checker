# Как устроен API Coverage Checker

Pytest не собирает страницу. `acc report` не запускает тесты.

## Установка и запуск

Перед началом подготовьте проект: установите Python версии 3.11 или новее, создайте и активируйте виртуальное окружение, установите зависимости проекта и используемый тестовый runner. Также должна быть доступна OpenAPI-спецификация в JSON/YAML — локальным файлом или по URL. Ниже предполагается, что нужное виртуальное окружение уже активировано.

При обычном использовании устанавливайте продукт в репозиторий, где находятся ваши API-тесты. Репозиторий API Coverage Checker не нужно копировать внутрь проекта с тестами. Например:

```text
my-project/
├── acc.yaml
├── openapi.yaml
└── tests/
```

Откройте терминал в каталоге `my-project/` и установите продукт с GitHub. Под `my-project` имеется в виду корневой каталог вашего продукта, где уже запускается привычная команда автотестов. Репозиторий API Coverage Checker не нужно помещать внутрь этого каталога.

```powershell
cd path\to\my-project
python -m pip install "git+https://github.com/avrelin-aleksey/api-coverage-checker.git"
```

Из каталога `my-project/` один раз выполните:

```powershell
acc init --api-key my-api --title "My API" --spec-file .\openapi.yaml
```

Команда сама создаст в текущем каталоге `acc.yaml`, `acc-journal/` и `acc-output/`. Если спецификация доступна по URL, вместо `--spec-file` используйте `--spec-url http://localhost:8000/openapi.json`. Существующий `acc.yaml` команда не заменяет без явного флага `--force`. Предполагается, что существующая настройка автотестов уже взаимодействует с чекером.

Сначала запустите привычную команду автотестов, затем из `my-project/`, где лежит `acc.yaml`, выполните:

```powershell
# Здесь запустите привычную команду автотестов вашего проекта.
acc report
Start-Process .\acc-output\index.html
```

`acc report` не запускает сервер и не открывает отдельное приложение. Он создаёт самодостаточную HTML-страницу `acc-output/index.html`, которую можно открыть обычным браузером. Повторный запуск состоит из тех же двух шагов: сначала тесты, затем `acc report`.

Для чистого прогона в PowerShell удалите накопленный журнал перед тестами:

```powershell
Remove-Item -Recurse -Force .\acc-journal
```

На Linux/macOS виртуальное окружение активируется командой `source .venv/bin/activate`, а отчёт открывается командами `open acc-output/index.html` (macOS) или `xdg-open acc-output/index.html` (Linux).

Для обновления продукта, установленного с GitHub, используйте то же виртуальное окружение, в котором установлен `acc`. В Windows PowerShell выполните из `my-project/`:

```powershell
.\.venv\Scripts\python.exe -m pip install --upgrade --force-reinstall --no-cache-dir "git+https://github.com/avrelin-aleksey/api-coverage-checker.git@main"

# Если нужно новое измерение, сначала запустите привычные автотесты проекта.
.\.venv\Scripts\acc.exe report
Start-Process .\acc-output\index.html
```

На Linux/macOS используйте соответствующие пути:

```bash
./.venv/bin/python -m pip install --upgrade --force-reinstall --no-cache-dir "git+https://github.com/avrelin-aleksey/api-coverage-checker.git@main"
./.venv/bin/acc report
```

Явные пути `.venv` важны: `pip` и `acc` из другой установки Python могут оставить в проекте старую версию чекера. Параметры `--force-reinstall --no-cache-dir` заставляют pip получить текущую ревизию из GitHub, а не использовать старую установленную копию. `acc init` повторно запускать не нужно: он используется только при первой настройке. Обновление не удаляет `acc.yaml`, `acc-journal/` и историю в `acc-output/history.json`. Сама установка пакета не меняет существующий HTML-файл, пока не выполнен `acc report`.

Если страница по-прежнему выглядит старой, проверьте установленную ревизию:

```powershell
Get-Content .\.venv\Lib\site-packages\api_coverage_checker-*.dist-info\direct_url.json
```

В файле должен быть текущий коммит GitHub, а не старый идентификатор. Открывайте отчёт только после выполнения `.\.venv\Scripts\acc.exe report`.

Если после обновления был новый прогон автотестов, сначала запустите привычную команду тестов, затем `acc report`. Если автотесты не запускались, `acc report` сохранит предыдущие данные при пустом журнале.

Если автотесты после обновления не запускались, `acc report` всё равно можно выполнить: когда `acc-journal/` пуст, он сохраняет последний отчёт и не заменяет счётчики и операции нулевыми значениями. Если в журнале есть вызовы, отчёт пересобирается по ним. Если журнал очищен и нужно получить новое измерение, перед отчётом снова запустите автотесты.

Сам репозиторий API Coverage Checker нужно клонировать только для разработки чекера или его UI. Для обычного взаимодействия с чекером достаточно установки с GitHub выше.

1. Тесты с декоратором пишут один JSON на вызов в `acc-journal/`.
2. `acc report` читает журнал и спецификацию и пишет `acc-output/index.html` и `acc-output/report.json`.

Файлы в журнале копятся. Перед чистым прогоном каталог `acc-journal/` нужно очистить, затем снова запустить тесты и `acc report`.

Декоратор сохраняет метод, статус, имена query и факт тела запроса или ответа. В шаблоне пути пишите путь из контракта, например `/users/{user_id}`, а не `/users/42`.

## Из чего складывается процент

Операция набирает долю из таких пунктов: сам вызов, каждый заявленный код ответа, тело ответа если оно заявлено, тело запроса если оно заявлено, каждое query-имя. Процент API — среднее по операциям, которые не попали в `skip`.

## Страница отчёта

В шапке переключаются язык и тема. Выбор темы запоминается в браузере. Кольцо сверху — **покрытие проверок**: среднее покрытие внутренних проверок активных операций, включая вызовы, коды ответов, тела и query-параметры. Три числа рядом — счётчики покрытия endpoint-операций:

- **Покрыто** — операции, которые тесты вызвали хотя бы раз.
- **Не покрыто** — операций без вызовов. Они снижают процент.
- **Игнорируется** — операции из правил `skip`. Они перечислены внизу страницы и на процент не влияют.

Операции разложены по тегам OpenAPI, в том порядке, как теги записаны в спецификации. Операция с несколькими тегами видна в каждом таком разделе. Без тега она попадает в «Без раздела».

Клик по операции открывает карточку. Каждый факт — цветная метка:

- Зелёная, **Использовано**.
- Красная, **Отсутствует**.
- Серая, **Не заявлено** — в контракте этого нет, это не дыра.

Так помечены тело запроса, каждый query-параметр, каждый код ответа и тело ответа, если контракт его описывает. У query-имени метка — только значок. Наведите на него, чтобы прочитать «Использовано», «Отсутствует» или «Не заявлено».

Наверху страницы линейный график — прогресс покрытия. Каждый `acc report` с измеренными вызовами дописывает точку в `acc-output/history.json`. Если журнал пуст и предыдущий отчёт уже есть, `acc report` сохраняет его и не добавляет дубликат. Журнал вызовов и этот файл — разные вещи: очистка `acc-journal/` график не стирает. Переключатель **Запуски / Дни / Недели / Месяцы / Произвольный период** меняет группировку. Для дня, недели и месяца берётся последний отчёт в каждом таком периоде. `history_limit` (по умолчанию 90) — сколько точек запусков хранить.

В режиме **Произвольный период** укажите начальную и конечную даты. Будущие даты недоступны, начало нельзя выбрать позже конца, а конец — раньше начала. Диапазон в один день даёт одну среднюю точку за день; диапазон от двух до четырнадцати дней — по одной средней точке на день; более длинный диапазон разбивается максимум на 14 равных интервалов. Интервалы без отчётов остаются на шкале без выдуманного значения, поэтому линия графика разрывается. Выбранные начальная и конечная даты всегда остаются на шкале. Рядом отображается изменение относительно предыдущего запуска. Кнопка **CSV** скачивает подробную таблицу со сводкой, историей и всеми операциями API. Кнопка **Скачать отчёт** сохраняет полную автономную HTML-страницу, которую можно распечатать в PDF из браузера.

## Порог внимания

Ползунок «Порог внимания» начинается с 10% и меняет только цвета, не пересчитывая проценты. Сводка раздела и покрытие endpoint-операций используют три диапазона: ниже половины порога — красный, от половины до значения ниже порога — жёлтый, порог и выше — зелёный. У отдельной операции процент ниже порога окрашивается красным. Сам ползунок не фильтрует список; отдельный фильтр «Ниже порога» использует выбранное значение.

`acc report --fail-under 80` — другая проверка. Команда всё равно пишет отчёт и завершается с кодом 1, если худший процент API ниже 80. Ползунок на странице этот порог не задаёт. То же ограничение можно записать в `acc.yaml` как `minimum_score: 80`. Если в команде передан `--fail-under`, берётся он.

## Как игнорировать

Правила `skip` пишутся у одного API. Пункт срабатывает, когда совпали все указанные в нём поля:

- `path` — путь из контракта. `*` — маска, например `/docs*`.
- `method` — `GET`, `POST` и остальные методы.
- `tag` — тег OpenAPI.
- `text` — маска по строке из метода, пути, описания и тегов, например `*internal*`.

Для каждого пути или метода, который нужно убрать из расчёта, добавляйте отдельный пункт списка. Отдельные пункты работают как «или», а поля внутри одного пункта — как «и». Например, этот фрагмент игнорирует два пути целиком, все операции `OPTIONS`, а для `/admin/users` — только `GET` и `POST`:

```yaml
apis:
  - key: shop
    title: Shop API
    spec_file: ./openapi.yaml
    skip:
      - path: /health
      - path: /metrics
      - method: OPTIONS
      - path: /admin/users
        method: GET
      - path: /admin/users
        method: POST
```

Если нужно игнорировать все методы одного пути, указывайте только `path`. Если нужно добавить несколько методов одного пути, повторите `path` в нескольких пунктах: одно поле `method` задаёт только один метод. Для группы путей используйте маску, например `/docs*`.

Внизу отчёта у проигнорированной операции написано, какое правило её убрало, и приведён YAML. Удалите этот пункт из `acc.yaml` и снова выполните `acc report` — операция вернётся в процент.

`acc config` печатает выбранный файл настроек и пути журнала и отчёта. Команду запускайте из каталога, где лежит `acc.yaml`.
